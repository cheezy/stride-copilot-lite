# Changelog

All notable changes to this project will be documented in this file.

## [0.4.0] - 2026-08-12

A parity release. `before_task` and `after_task` never fired on GitHub Copilot CLI — the runtime this plugin is named for — and `after_goal` did not either, so the entire hook layer was inert there. This release makes all three work, then builds the workflow features that only matter once they do: a decision matrix, task enrichment, hook-failure triage, step telemetry, and three optional cross-plugin integrations. Four pre-existing defects in the hook executors were found and fixed on the way, three of them in the PowerShell mirror.

**Breaking:** the four skill directories were renamed, so anything referencing a skill by name must be updated; and anyone driving a goal directory with their own orchestrator rather than the shipped workflow skill must now write the boundary marker for `before_task` / `after_task` to fire under Copilot.


### Fixed

- **`test/smoke.sh`'s init-template byte-parity assertion was vacuous** — it compared one extraction with itself, so it could not fail. With the init skill's directory moved aside it still passed, because empty equals empty, while three neighbouring assertions correctly failed. The parity guarantee the v0.2.0 entry advertises as the fix for template drift was therefore not being enforced at all. The assertion now compares two **independently derived** copies: the expectation uses the original forward-scanning extractor, and the simulated init flow uses a second one that bounds the section and tracks the four-backtick fence explicitly. It is credited only when both sides are non-empty, all five structural markers are present, and the extraction carries exactly the template's four `## ` headings — that last guard catching over-capture, which is truncation's mirror and which neither extractor notices alone, since removing the closing fence makes both run to EOF in agreement. Two negative controls prove the comparison has teeth rather than merely reporting green: a one-byte perturbation must be detected as a difference, and an empty side must be refused rather than compared. Verified by four intentional-break checks — a missing skill directory, a broken opening fence, a broken closing fence, and a deliberate bug in one extractor — each failing the parity assertion specifically.


- **`before_task` and `after_task` now fire under GitHub Copilot CLI.** They previously keyed on Claude Code's `Agent` subagent-dispatch tool call, and Copilot CLI emits no skill- or agent-dispatch event at all, so two of the three hooks never fired on the runtime this plugin is named for. The workflow skill now writes a one-line boundary marker to `.stride-copilot-lite/lite-boundary` at Steps 2 and 5, and `hooks.json` registers PreToolUse on `Edit|edit` / `Write|create` so that write is the intercept. Routing requires **both** the exact marker path and the exact boundary token, so writing the token into any other file — or naming it in a shell command — fires nothing. The `Agent` route is retained unchanged for Claude Code; when both events occur the marker route fires first and records the boundary, and the `Agent` route consumes that record and stands down, so each boundary fires exactly once. The chosen intercept and the two rejected alternatives (a Bash sentinel command; keying on the workflow's own file mutations) are recorded in `AGENTS.md` → "Hook intercept design". **Breaking for anyone driving a goal directory with their own orchestrator** rather than the shipped workflow skill: the marker write is now required to fire `before_task` / `after_task` under Copilot.
- **`after_goal` never fired under Copilot CLI either.** The bash executor's field extractor looked for a real `"` and Copilot delivers tool arguments as a JSON-*encoded* string (`\"file_path\":\"…\"`), so every Copilot-shaped payload silently routed to nothing — including `after_goal`, which the README, AGENTS.md and the v0.1.0 CHANGELOG entry all described as working on both runtimes. The extractor now falls back to an unescaped view of the payload. The PowerShell executor already decoded `toolArgs` correctly and was unaffected. All three hooks are now live on both runtimes.
- **The PowerShell executor could not read its stdin at all.** `stride-copilot-lite-hook.ps1` is invoked as `pwsh -File … <phase>` with the payload piped in, and a `-File` script whose `param()` block declares no pipeline-bound parameter cannot bind piped input — PowerShell raised "The input object cannot be bound to any parameters" and the automatic `$input` stayed empty, so every trigger no-opped under every runtime. It now reads `[Console]::In.ReadToEnd()`, which sidesteps parameter binding. This is what the PowerShell harness had been reporting: it went from 3 passed / 7 failed to fully green.
- **The PowerShell executor never actually ran multi-word hook commands.** It invoked `Start-Process -FilePath bash -ArgumentList '-c', $command`, and `-ArgumentList` re-splits on spaces — so `bash -c "echo hi"` reached bash as `-c echo hi` and ran `echo` with no arguments. Any hook command containing a space did nothing while the executor reported `"status":"success"`, which is worse than failing. Replaced with `ProcessStartInfo.ArgumentList`, which passes each argument verbatim with no shell re-parsing (and, with `UseShellExecute=$false`, is also what lets the child inherit the exported variables above). Only single-word commands such as `false` had been behaving correctly, which is why the exit-code harness cases passed while real hooks silently no-opped.
- **A failing blocking hook did not stop the workflow under Copilot CLI.** Claude Code blocks a PreToolUse call on `exit 2`, but Copilot CLI ignores exit codes and blocks on a stdout `{"permissionDecision":"deny"}` object, so a failed `before_task` fired and then let the workflow continue. Blocking failures now emit both — the `permissionDecision` / `permissionDecisionReason` keys ride inside the same single-line failure JSON, which consumers that don't know them simply ignore. `after_goal` stays advisory and never emits a deny.

#### Fixed — the failed-verdict `note` rule the server already enforces (D240)

This port's task-reviewer prompt described `note` as optional on every section verdict. The completion API has required it on a `"failed"` verdict since D231, and enforces that **unconditionally** — independently of the `strict_completion_validation` flag — so an agent on this runtime could emit a note-less failed verdict that its own prompt endorsed and be rejected with a `422`. The rejection is self-describing and recoverable, so nothing was broken; every such completion simply paid an avoidable round trip.

The prompt now states that on a `"failed"` section verdict `note` is **REQUIRED** and must name the specific violation or gap in at least **20 non-whitespace characters**, carries the anti-placeholder prohibition (no stub, `TODO`, empty string, or bare restatement of the status), and directs that an empty note means the *verdict* is wrong rather than that the note is unnecessary. `note` stays **optional** on `"passed"` and `"not_assessed"`, so the ordinary empty-section case gains no friction.

Producer-side only: the server-side check in `Kanban.Tasks.CompletionValidation.ReviewContract` is unchanged, and no port was accommodated by weakening it.

### Added

- **Added anti-rationalization scaffolding to all four skill files.** The workflow skill gains a **Rationalization table** and a **Quick reference card** alongside its existing Red flags and Pitfalls; `create-goal`, `create-task` and `init` each gain a Red flags section and a Rationalization table of their own. Thirty-one rows in total, each naming an excuse, the fact that refutes it, and the concrete consequence of acting on it.

  **The rows are written for this plugin, not copied.** They come from failure modes it actually has — resolving the decision matrix before enrichment (which routes the thinnest task to `skip-all`), force-approving at the review cap, retrying a boundary write to get past a blocking hook, leaving the activation marker behind, the decomposer's 1–8 cap, the never-diverge template rule, the `(none)` placeholder's meaning, the `.stride_lite.md` filename compatibility promise, and the gated integrations' skip-is-free semantics. Nothing references an API endpoint, a root key or a review queue: an irrelevant row trains agents to skim the table, which costs more than the row is worth, so `test/smoke.sh` asserts none is present.

  **Two rows are security-bearing and are marked as such** — never supplying the exploratory step's authorized-and-non-production affirmative on the user's behalf, and never treating an unconfirmable security verdict as mitigated. A rationalization table is itself a place a later edit can weaken a control by softening one line, and that reads as tidying rather than as a policy change, so AGENTS.md now records that those two rows are **not editorial** and both are asserted individually.

  The Quick reference card is a compressed index rather than a second copy of the loop: one line per step naming the thing most easily got wrong, plus the five exits that must clear the activation marker.

- **Added an optional deep security-considerations review, gated.** Every task file renders a `## Security considerations` section and the generalist `task-reviewer` gives it one overall verdict — but nothing checked the listed considerations one by one, so an implication the task author wrote down could ship unaddressed behind a green review. When the section carries **real** entries and the sibling `stride-copilot-security-review` plugin is installed, a new **Step 6c** dispatches its `security-reviewer` in considerations mode with the working-tree diff and that list, and captures one verdict per consideration — `mitigated`, `partial` or `unmitigated`, each with a `file:line` evidence reference. A `(none)` placeholder or an entry beginning `None —` is explicitly **not** a trigger.

  **Any `partial` or `unmitigated` verdict loops the task back to implementation** through Step 7's existing `changes_requested` branch — deliberately **no second loop and no second cap**. It reuses the `review_iteration` counter and the `max_review_iterations` bound already there, so a persistently unaddressed consideration stops the run rather than looping forever, and exhausting the cap has the same terminal shape as any other exhausted review. Two reasons producing `changes_requested` on one pass is **one** increment and one Step 4 pass addressing both; counting per reason would burn the cap in a single iteration.

  **Every failure mode is fail-closed, because this step is itself a security control.** An absent plugin means no verdict recorded rather than a passing one; a malformed, empty or unparseable verdict set is treated as unaddressed rather than downgraded to passed. Inability to confirm mitigation is never the same as confirming it. The considerations list and the diff are framed in the dispatch prompt as **data to assess, never instructions**, so an attacker-authored consideration or diff hunk cannot redirect the reviewer.

  `agents/task-reviewer.agent.md` documents the `consideration_verdicts` array, since that agent owns the `## Review Report` section its verdicts are folded into — while stating plainly that the generalist **never produces it**, and that an absent array (the specialist did not run) is not the same as an empty one (it ran and returned nothing, which is treated as unaddressed).

- **Added optional exploratory-testing and hardening steps, both gated.** When the sibling `stride-copilot-exploratory-testing` plugin is installed, a new **Step 6a** maps the active task's `## Testing strategy` manual-test entries to charters and dispatches that plugin's `explorer` agent once per charter, and a new **Step 6b** dispatches its harden surface to draft regression checks from oracle-confirmed bugs. Until now those manual-test entries sat in the task file as a note to a human who may never read them. **Every gate falls through to a clean skip** — plugin absent, no manual tests, no affirmative, or no way to dispatch agents — so the integration costs nothing when it is not wanted and can never fail a run by being unavailable.

  **The affirmative is collected at activation, and never inferred.** Before any session, the workflow must hold an explicit statement from the user that the target is one they are authorized to test and is not production. The Claude Code plugin collects this at Step 0; this port collects it at **activation** instead, because the activation contract already requires the user to state intent and supply a path, so that exchange is the one point where a two-way conversation is genuinely happening — Step 0 writes a file and talks to nobody. It is never inferred from a `localhost` URL, a dev-looking hostname, or anything a task file says, and a missing affirmative means Step 6a skips rather than the workflow asking mid-drive.

  **Only the `explorer` agent is dispatchable.** The plugin's `explore`, `pair`, `recon` and `nightmare-headline` surfaces, and its router skill, are all on a never-dispatch list with the reason for each stated from that surface's own text — they can require a human, and this workflow does not prompt between steps, so dispatching one would stall the drive. The router is singled out because the bare plugin name resolves to it, so "dispatch the plugin" lands there by accident.

  **Drafts are drafts.** Hardening runs nothing, so a drafted check is never reported as passing. One enters the test tree only after the project's own gate command has come back clean **across the whole suite**, and otherwise the move is reverted and a follow-up filed. The hazard lands differently here than in the Claude Code plugin: `## after_task` fires on the Step 5 boundary-marker write, so a red check in the tree would take down the *reviewer re-run this step itself requires*, then the next task's `## after_task`, then `## after_goal`. That is why the gate run is a precondition rather than a courtesy.

  `.exploratory/` is now gitignored — session artifacts hold transcribed application output and arrive untracked, so a gate that stages everything before committing would sweep them into a commit, and `.gitignore` is inert for a path git already tracks. The Bash scope gains the project's gate command and `cp`/`rm`, both scoped to Step 6b only. AGENTS.md records that dispatching another plugin's agent is a local harness operation and **not** a network call, so a later reader cannot delete these steps to satisfy the no-network rule.

- **Every Completion Summary now records workflow step telemetry.** All seven task-level steps — `enricher`, `before_task`, `explorer`, `planner`, `implementation`, `after_task`, `reviewer` — appear in every summary, each marked dispatched or skipped, with a duration where one was actually measured and a reason naming the causing condition where it was not. A skipped step is **recorded, never omitted**: once the decision matrix started skipping steps, a summary with no explorer mention became ambiguous between "the matrix skipped it" and "the agent forgot", and omission is precisely the shortcut telemetry exists to catch. A reason must name the rule (`"Decision matrix: small complexity, 1 key file → skip-all row"`), not restate the outcome (`"explorer was skipped"`). It renders as a human-readable table plus an embedded fenced JSON block for tooling — the same dual shape `task-reviewer` already uses — with the table as the primary carrier.

  **The vocabulary is this plugin's own.** There is no `after_doing` or `before_review`; those are the full Stride plugin's hook names and recording them here would produce telemetry comparable to nothing. `after_goal` is excluded too — it is goal-level, fires once per goal, and belongs in `goal.md`'s summary. Durations are recorded only where measured: the hook executor emits `duration_seconds`, so `before_task` and `after_task` have real figures, while a subagent dispatch usually does not and is recorded as dispatched with the duration omitted rather than invented. Telemetry carries step names, durations and reasons only — no command output, no environment values, no paths outside the project, since the summary is committed.

  **The Concrete walkthrough was rewritten alongside it.** It had drifted badly: it still described `## before_task` firing on the Step 3 subagent dispatch, which stopped being true when the boundary-marker intercept landed earlier in this release, and it predated Steps 1a and 3a entirely. It now walks the real sequence — marker write, enrichment check, matrix resolution, the boundary writes that fire the hooks, the `full` and `explore-review` branches, and the marker clear — and carries a complete telemetry block for each of its two tasks, one of which shows a planner skip with the rule that caused it.

- **Deepened both hook test suites to cover the behaviour this release added.** The harnesses previously covered routing and the exit-code contract; three of this release's changes put substantial new behaviour into the hook layer that nothing exercised. They now cover every branch of the runtime-native trigger including four documented near-misses, env-var derivation for all nine exported keys in both the derived and undeterminable branches, metacharacter inertness, every marker-gate branch plus the override, section-parsing edge cases (a missing section, an empty fenced block and a comment-only block each no-op), and the failure partition — that a command list stops at the first failure and that `commands_completed` + the failed command + `commands_remaining` reconstruct the section exactly, asserted by an observable side effect rather than only by the JSON's own account of itself. The bash suite goes 13 → 49 assertions and the PowerShell mirror 10 → 46.

  **A cross-executor JSON parity check is the new part.** A shared fixture set — every trigger shape, both runtimes' field casing, a blocking failure and the advisory path — runs through both executors under both an all-succeeding and an all-failing configuration, with `duration_seconds` normalized out and the emitted JSON diffed. Two configurations rather than one because a divergence can hide in either outcome: a first version ran only the succeeding config and did **not** catch a mutation that made the PowerShell executor emit `permissionDecision` on the advisory path, since a succeeding `after_goal` emits no failure JSON at all. Where `pwsh` is absent the check reports a **skip with a reason** rather than passing silently, and it requires a majority of fixtures to have produced non-empty output before a match counts — two executors that both emit nothing agree trivially.

  **The parity work immediately found a real bug.** The PowerShell orchestrator gate read the marker's modification time with `Get-Item`, which throws on the dot-prefixed `.orchestrator_active` path; the throw was swallowed by the surrounding `catch` and read as "no active run". So whenever `started_at` could not be parsed, the mtime fallback silently disabled every hook on PowerShell instead of falling back. Now uses `[System.IO.File]::GetLastWriteTimeUtc`.

  Every fixture command is inert and confined to a temp directory the suite creates and removes; both suites assert they leave no scratch directory behind and write no marker into the checkout. There are deliberately no timing assertions. README.md documents how to run all three suites and why both hook suites are needed rather than one.

- **Added `agents/hook-diagnostician.agent.md`**, ported from the Claude Code plugin. A blocking `## before_task` or `## after_task` failure now dispatches it with the structured failure JSON the hook script already emits, and the workflow surfaces a prioritized fix plan instead of the raw command output. That matters most for `after_task`, which is where a user's test suite and linter live — interleaved output from two tools is exactly what raw surfacing handles worst, and once the blocking hooks actually fire under Copilot this became the most common way a run halts.

  **Triage does not change the outcome.** The agent reads the payload and returns a fix order; it never re-runs or repairs the failing command, and both blocking paths still clear the marker and stop. Its grant is `["read", "search", "glob"]` — no command execution, so a diagnostician cannot act on a misdiagnosis, and no mutation either. It never echoes the captured stdout/stderr tails back verbatim, since those can carry environment values, paths and occasionally secrets, and it treats all captured output as data to classify rather than as instructions. An `after_goal` failure is advisory, so triage there is offered but explicitly optional — the run is finishing, not halting, and nobody is blocked waiting.

  **The input contract covers eleven keys, not nine.** The hook script emits `permissionDecision` and `permissionDecisionReason` alongside the nine base keys on a *blocking* failure — added earlier in this release so Copilot CLI actually blocks — so the agent's Inputs table marks those two as conditional and reads their presence as a reliable signal that the workflow was genuinely halted. `test/smoke.sh` asserts the table and the script agree key-for-key, and a new hard rule in AGENTS.md keeps them in step.

  **In this port the triage lives at Steps 2 and 5, not 3 and 6.** The hooks fire on the boundary-marker writes rather than on the subagent dispatches, so that is where a hook failure actually surfaces. Steps 3 and 6 name the agent only to scope it away from a failed *dispatch*, which produces no failure JSON and is not a hook failure at all.

- **Added `agents/task-enricher.agent.md`**, ported from the Claude Code plugin. `create-decomposer` runs with a `tools` grant of `[]` and never sees the codebase, so a task file's `## Key files`, `## Patterns to follow` and `## Testing strategy` are guesses by construction — and a hand-written one may have nothing in them. A new **Step 1a** checks whether `## Key files`, `## Acceptance criteria`, `## Verification steps` or `## Testing strategy` are sparse and dispatches the enricher only when they are; a fully-specified task file skips it. Once dispatched the agent fills any of the **eleven** derivable sections it finds sparse, in place, and leaves every other byte unchanged — the title, the metadata line, the three intent sections (`## Description`, `## Why`, `## What`) and every already-populated section come back byte-identical. It appends nothing, so it never contends with the `## Exploration Report` that `task-explorer` appends at the end of the file.

  Its grant is `["read", "search", "glob", "write"]` and **both omissions are deliberate**: no command execution, because an agent that rewrites files has no business holding it; and no `edit`, because a section-by-section streaming walk would leave a half-enriched task file behind on any failure — and that file is what the whole workflow reads. Read-whole/write-once is enforced by the tool list rather than merely promised in prose. The agent also refuses to write at all when the target is ambiguous (a duplicated owned heading, no `# ` title, or a `goal.md` basename — which would additionally fire the user's `## after_goal` hook), and never copies a credential, `.env` content or internal hostname into a section, since task files are committed.

  **Ordering is load-bearing and differs from the Claude Code plugin's.** Enrichment runs *before* the decision matrix resolves, because a sparse file counts zero key files and would otherwise take the `skip-all` row on precisely the task whose metadata was too thin to judge. Since this port resolves the matrix at Step 1a rather than Step 3 (its hooks fire on the Step 2 and 5 boundary writes), the matrix is resolved at the *end* of Step 1a, against the enriched file. `test/smoke.sh` asserts that ordering directly rather than trusting the prose.

  The sparse rule is worded identically in the agent and in the workflow, and the smoke suite asserts that: a definition that drifts between the gate and the agent is how a task ends up neither enriched nor reviewed. The suite also asserts that the agent's owned ∪ protected sets are exactly the task template's fourteen headings and are disjoint, so a template change cannot silently leave a heading the enricher will neither fill nor protect. 45 → 67 assertions.

- **The workflow loop now scales to the task via a decision matrix.** `stride-copilot-lite-workflow` previously dispatched `task-explorer` and `task-reviewer` on every task unconditionally, and hard-coded a Red Flag forbidding the agent from skipping the explorer for a small task. It now resolves one branch per task from the task file's complexity and its `## Key files` count — `small` with 0–1 key files skips explore, plan and review; `small` with 2 or more explores and reviews; `medium`, `large` and any unreadable signal do all three — and gates Steps 3 and 6 on it. A **new Step 3a** adds the planning branch the plugin lacked, for `medium` and `large` only; the eight steps are not renumbered, since the README, AGENTS.md and the hook trigger table reference them by number. Every skipped step is recorded in the task's `## Completion Summary` with the rule that caused it, because an unrecorded skip is indistinguishable from a bug. The Red Flags section now forbids overriding the matrix by intuition — in either direction — rather than forbidding any skip at all.

  Two consequences worth stating plainly. **The branch is resolved at Step 1, not Step 3** as in the Claude Code plugin: this port fires its hooks on the boundary-marker writes at Steps 2 and 5, which precede each dispatch, so the branch has to be known before Step 2 or the `skip-all` row would still pay both blocking hook runs. **And a skipped boundary takes its hook with it** — on the `skip-all` row neither `## before_task` nor `## after_task` runs, so a user's `git pull`, tests or linters do not execute for that task. That is the second half of the saving and the least obvious thing the matrix does, so the Completion Summary must name the unfired hook and not merely the skipped step.

  **No template change was required.** The `> Type: … · Complexity: … · Priority: …` metadata line the matrix reads already exists in both plugins' task templates, and the two `fixtures/expected-output/task1.md` files are byte-identical — so the never-diverge rule between the two create skills, and the README's byte-identity promise to stride-lite users, are both untouched.

- **Added `lib/select_workflow_branch.md`**, ported from the Claude Code plugin as the normative reference implementation of the matrix. It resolves a rendered task file to one of `skip-all` / `explore-review` / `full`, never fails, and treats both signals as data that selects a branch rather than as instructions. `test/smoke.sh` extracts the reference implementation from the spec at runtime — rather than hand-copying it as the other four helpers are — so spec and tested code cannot drift, and asserts every matrix row plus the safe-default rules against independently written expectations. The suite goes from 26 to 45 assertions.

- **Hook firing is now scoped to an active workflow run.** The workflow skill writes `.stride-copilot-lite/.orchestrator_active` at a new Step 0 and clears it on all five exit paths — clean completion, goal-already-complete, the malformed-goal-directory hard errors, an explorer or reviewer dispatch failure, and the review-iteration cap. The executor runs a `.stride_lite.md` section only when that marker exists and its `started_at` is within 4 hours; missing or stale means run nothing and exit 0, never blocking the tool call. `STRIDE_COPILOT_LITE_ALLOW_DIRECT=1` bypasses the gate for debugging and CI. This is a direct consequence of the runtime-native intercept above: any event Copilot CLI actually emits is broader than a subagent dispatch, so without the gate an ordinary file edit could run a user's `git pull` or test suite outside any workflow. **The marker is a coordination mechanism and not a security boundary** — any local process can write it, and nothing may lean on it for authorization; `AGENTS.md` states this explicitly so a later change cannot quietly repurpose it.

- **Moved this plugin's run state into its own `.stride-copilot-lite/` directory.** The boundary marker and its fired-record previously lived under `.stride/`, which belongs to the full Stride plugin — a project with several of these plugins installed would have had them sharing a directory, letting one plugin's lifecycle arm or disarm another's hooks. The directory also sits outside the goal directory so Step 8's terminal PENDING→IMPLEMENTED move cannot carry it along, and it is gitignored.

- **Hook commands now receive task and goal context as environment variables.** Each `.stride_lite.md` command runs with `HOOK_NAME`, `AGENT_NAME`, `TASK_FILE`, `TASK_NUMBER`, `TASK_TITLE`, `GOAL_DIR`, `GOAL_FILE`, `GOAL_SLUG` and `GOAL_TITLE` exported, all derived from the goal and task markdown and their paths — there is no server involved. Previously nothing was forwarded, so a variable-using hook carried over from the Claude Code plugin (which the README markets as a migration feature) silently interpolated empty strings. A key that cannot be derived exports as the empty string rather than erroring, so referencing one is always safe including under `set -u`, and no derivation failure changes a hook's exit code. Values are exported as environment values and never spliced into command text, so a task title containing `$(...)` or backticks is inert. Paths taken from the hook payload are resolved and confirmed to sit under the project directory before being read. The set deliberately omits the full plugin's `BOARD_ID` / `COLUMN_NAME` / `TASK_STATUS` — this plugin has no board, column or status, and exporting them empty would teach a contract that does not exist. To carry the active task, the boundary marker gains an optional trailing path (`stride-lite-boundary:before_task:<taskN.md>`); a marker without one still fires the hook and simply yields empty task variables.

- Hook-harness coverage for the new trigger in both executors: the marker route on both payload shapes, four distinct near-misses (marker path without a token, token written to another file, marker payload in the wrong phase, token inside a bash command), the fire-exactly-once handshake and its consume-on-fire release, the blocking deny-plus-exit-2 contract, the advisory no-deny contract, and a regression guard for `after_goal` on a Copilot-shaped payload. The bash harness goes from 13 to 25 assertions and the PowerShell harness from 10 to 22.

### Changed

- **Renamed the four skill directories and identities `stride-lite-*` → `stride-copilot-lite-*`**, finishing the plugin rename that v0.3.0 started. The skills formerly named `stride-lite-create-goal`, `stride-lite-create-task`, `stride-lite-init` and `stride-lite-workflow` now live at `skills/stride-copilot-lite-create-goal`, `skills/stride-copilot-lite-create-task`, `skills/stride-copilot-lite-init` and `skills/stride-copilot-lite-workflow` (moved with `git mv`, so rename history is preserved); each `SKILL.md`'s frontmatter `name` matches its directory, and every cross-reference in `README.md`, `AGENTS.md`, the three `agents/*.agent.md` files, `lib/parse_args.md`, `lib/slugify.md` and `test/smoke.sh` was updated to match. This also removes the `stride-copilot-lite:stride-lite-workflow` split-identity construction from the README. **Breaking for name-based references:** anything that names a skill directly — a `.stride_lite.md` hook body, your own scripts, CI, or documentation — must use the new `stride-copilot-lite-*` names. Skill *activation* is unaffected: Copilot matches natural-language prompts against each `SKILL.md` description block, not against the skill or directory name, and the description prose is unchanged apart from the renamed identifiers themselves.
- Earlier entries in this file were updated to the new skill names so no reference to this plugin's own surface uses the old prefix. Entries prior to this one describe releases in which those directories were still named `stride-lite-*`.

## [0.1.0] - 2026-05-27

### Added

- Initial scaffold for the GitHub Copilot port of [stride-lite](https://github.com/cheezy/stride-lite): `plugin.json`, `README.md`, `CHANGELOG.md`, `AGENTS.md`, `LICENSE`, `.gitignore`, and the empty subdirectory tree (`lib/`, `agents/`, `skills/`, `hooks/`, `test/`, `fixtures/`, `docs/`).
- `plugin.json` follows the `stride-copilot` manifest shape (root-level, not `.claude-plugin/plugin.json`), with `name=stride-copilot-lite`, `version=0.1.0`, `license=MIT`, and the `agents` / `skills` / `hooks` pointer fields populated for Copilot's plugin loader.
- Four skills (`stride-copilot-lite-create-goal`, `stride-copilot-lite-create-task`, `stride-copilot-lite-init`, `stride-copilot-lite-workflow`), three subagents (`create-decomposer.agent.md`, `task-explorer.agent.md`, `task-reviewer.agent.md`), four `lib/` markdown helpers, and a `hooks/` enforcement layer (`hooks.json` + `stride-copilot-lite-hook.sh` + `stride-copilot-lite-hook.ps1`) ported from stride-lite under W924–W928.
- Smoke test (`test/smoke.sh`, 26 assertions, byte-identical with stride-lite source) and a compact 13-case bash hook test harness (`hooks/test-stride-copilot-lite-hook.sh`) covering missing-file no-op, both Claude Code snake_case and Copilot CLI camelCase field-name handling, all three hook trigger conditions, env-var defaulted-fallback when `CLAUDE_PROJECT_DIR` is unset, non-matching tool / non-stride-copilot-lite subagent no-ops, and the failing-command exit-code contract (before_task/after_task block with exit 2, after_goal stays advisory at exit 0, all emitting failure JSON). PS1 mirror (`hooks/test-stride-copilot-lite-hook.ps1`) ships for Windows CI.
- README, AGENTS.md, and CHANGELOG finalized for the Copilot CLI install + migration story. README documents the `copilot plugin install` flow, the four-skill activation reference, the `.stride_lite.md` configuration shape with a hook-firing table, and a stride-lite → stride-copilot-lite migration guide. AGENTS.md preserves the stride-lite hard-rules block with the Copilot-variant repository layout.

### Removed

- No `commands/` directory. GitHub Copilot CLI has no Claude Code-style slash command surface; skill activation is done by natural-language prompt matching against the four `SKILL.md` description blocks. README documents the activation phrases for each skill.

### Backward compatibility

Initial release — no prior version of stride-copilot-lite exists. Behavior parity with `stride-lite` is the goal of subsequent releases; this 0.1.0 entry only establishes the metadata foundation.
